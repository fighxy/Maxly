# Локальная база iOS-клиента

## Схема

| Модель | Поля | Связи |
|---|---|---|
| `SDChat` | id, title, type (private, group, channel), lastMessageId, unreadCount, updatedAt, preview | messages, каскадное удаление |
| `SDMessage` | id, serverId, chatId, authorId, text, timestamp, status (sending, sent, failed), mediaId | chat, media (nullify) |
| `SDUser` | id, name, avatarUrl | нет |
| `SDMediaItem` | id, type (image, video, audio, file), url, size, localPath | нет |

Все `id` уникальны (`@Attribute(.unique)`). В `SDMessage` лежит и связь `chat`, и поле `chatId`: по полю быстрее фильтровать. Перечисления берутся из `OrbitlDomain` и хранятся строками (`*Raw`), чтобы новые значения не ломали схему. Контейнер создаётся в `SwiftDataStack`, который умеет работать в памяти для тестов. Контейнеры создаются строго по одному (общий замок), у каждого своя `Schema`, а у контейнера в памяти своё имя: параллельное создание в тестах роняло процесс с signal 11. При выходе чаты и сообщения стирают сами репозитории (`removeAll`), а пользователей и медиа — `eraseUsersAndMedia()`.

## Почему SwiftData

SwiftData встроена в iOS 17+, работает со Swift 6 и SwiftUI, не требует сторонних зависимостей, а через `ModelActor` даёт фоновые записи без гонок данных. Модели остаются внутри `OrbitlData`, а наружу выходят только доменные типы и Sendable-записи (`ChatRecord`, `MessageRecord`). Поэтому базу можно заменить, не трогая экраны. **Риск:** производительность на десятках тысяч сообщений нужно проверить прототипом (architecture.md, «iOS-клиент»).

## Swift 6 и потоки

Репозитории `ChatRepositoryImpl` и `MessageRepositoryImpl` — акторы, которые реализуют `ModelActor` вручную (макрос `@ModelActor` не умеет инициализатор с `api`). У каждого свой фоновый `ModelContext`. Модели SwiftData не Sendable и не покидают актор, наружу выходят доменные типы и записи. Главного контекста нет: экраны читают только через подписки репозиториев.

- **Запись пакетом.** `upsert` одним запросом выбирает все уже известные строки пакета (предикат `IN` по id и по серверному id) и сохраняет контекст один раз.
- **Очистка и поздние ответы.** `removeAll` увеличивает счётчик поколений. Ответ сервера на запрос, начатый до очистки (`refresh`, `loadMore`, `fetchLatest`), в базу не пишется и завершается `.cancelled`: данные прошлого аккаунта не возвращаются после выхода.
- **Подписки.** Подписчик, чей поток уже завершён, не запоминается, завершённые потоки удаляются в `onTermination`.

## Пагинация

Используется курсор по `timestamp`. Страница содержит `pageSize` (50) сообщений строго старше курсора, от новых к старым (`page(chatId:before:limit:)`). Экран подписан на `messages(chatId:)` и получает последние N сообщений чата. `loadOlder` увеличивает N на страницу, а если в кэше старше не хватает сообщений, догружает историю с сервера, начиная от самого старого показанного сообщения.

## Синхронизация с сервером

Схема такая: сначала кэш, потом фоновое обновление.

1. Подписка на `chats()` или `messages(chatId:)` сразу отдаёт данные из базы.
2. `refresh()` и `SyncEngine` в фоне запрашивают сервер и пишут результат через `upsert(_:)`.
3. После каждой записи репозиторий заново отдаёт снимок всем подписчикам, и экран обновляется сам.
4. Исходящее сообщение сначала записывается со статусом `sending` и локальным id, затем уходит через `OutboxQueue`. После ответа сервера статус меняется на `sent`, при ошибке на `failed`; `retry(messageId:)` ставит `failed` в очередь снова. Если эхо своего сообщения (пуш или опрос) пришло раньше ответа на отправку, при `sent` лишняя строка с тем же серверным id удаляется, дубля не остаётся.
5. `SyncEngine` пишет пуши ядра сразу: новое и изменённое сообщение, удаление, обновление чата, своя отметка прочтения. «Печатает» в базу не кладётся. Опрос раз в 30 секунд остаётся запасным путём и не запускается, пока нет сети (`networkLost` до `networkRestored`). `stopEvents()` дожидается пушей, которые уже пишутся, без активного ожидания.

## Правила слияния

Пуши приходят не по порядку и бывают неполными, поэтому строка чата не перезаписывается целиком.

- **Обновление чата** (`upsert`): пустой заголовок не затирает известный; пустые `lastMessageId` и превью оставляют прежние; запись старше строки (`updatedAt` меньше) не меняет превью, последнее сообщение, время и счётчик; отрицательный счётчик считается нулём.
- **Новое сообщение**: превью и время меняются, только если сообщение не старше строки. Счётчик растёт только для чужого сообщения, которое действительно вставлено: повтор того же пуша его не увеличивает. Сообщение в неизвестный чат подтягивает строку чата с сервера.
- **Правка**: меняет текст только уже известного сообщения (новое не создаётся) и превью, только если это последнее сообщение чата. Чат в списке не поднимается.
- **Удаление**: если удалено последнее сообщение, строка обновляется с сервера; без сети превью берётся из самого свежего сообщения в кэше.
- **Прочтение**: пуш прочтения собеседника наш счётчик не трогает. Своя отметка с другого устройства обнуляет счётчик, только если она не раньше последнего сообщения строки; «пометить непрочитанным» оставляет хотя бы 1.
- **Свои сообщения**: при постановке в очередь строка сразу получает превью и время, после ответа сервера ещё и `lastMessageId` (серверный id, чтобы отметка прочтения не ушла с локальным).
- **Отметка прочтения**: `markAsRead` не ходит на сервер, если непрочитанных нет. Ошибка сервера не откатывает локальный ноль.
- **Удаление чата** забирает и сообщения, записанные до появления самого чата (без связи `chat`).
